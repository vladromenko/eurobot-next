# Что подключить и как затем загрузить прошивку

Это инструкция для владельца робота. В ходе её подготовки устройство не подключалось, Flash не читалась и не записывалась, моторы и насосы не запускались. Текущие host/ASan/ARM и ROS проверки прошли; протокол и журналы — в VALIDATION_REPORT. Перед самостоятельной записью образ и manifest должны соответствовать текущему source/deployment. Исторический или изменённый образ отклоняется проверкой source fingerprint.

## Куда подключить провода на показанной плате

Пошаговая карта всех разъёмов, новая установка8 насосов/8 клапанов и13 входов: [BOARD_WIRING.md](BOARD_WIRING.md). Пользовательская красная обводка не задаёт назначение.

- **Прошивка:** маленький `SWD` над STM32. Соединить ST-LINK GND→GND, NRST→NRST, SWCLK→SWCLK, SWDIO→SWDIO. Это четыре подписанных контакта. На показанном разъёме **нет VTref**; если модель ST-LINK требует его, нужна отдельно подтверждённая точка3.3V.
- **Команды с Mac:** верхний `USART1`: GND→GND USB-UART, RX платы←TX адаптера, TX платы→RX адаптера. Уровни3.3V,115200/8N1. Провод питания адаптера без схемы не подключать.
- **Питание:** нижний `Power Supply Input` подписан GND/+6V/+12V. Это отдельные силовые шины; не перемыкать их. Какая шина питает стабилизатор логики, карта не определяет. +5V на соседних разъёмах не является найденным входом питания MCU или VTref.
- **Насосы/клапаны:** правые `Power Output`: минус нагрузки к её POx, плюс к выбранной по номиналу шине +6V либо+12V. POx — транзисторный ключ низкой стороны, не положительное питание. Для новой8+8 установки предлагаются пары PO1/2…PO15/16; это будущая проводка, не утверждение о существующем жгуте.
- **Колёса:** `RS-485 (USART6)` GND/A/B к внешним Maxon-контроллерам, не USART1. Питание/терминация внешних контроллеров проверяются отдельно.

Подробные таблицы исключают подключение по случайному номеру контакта, но не заменяют подтверждение питания, тока и механических ограничений.

## Два разных канала

| Задача | Устройство на Mac | Интерфейс STM32 |
|---|---|---|
| Запись и чтение Flash | ST-LINK через USB, STM32CubeProgrammer | Показанный SWD: GND, NRST, SWCLK, SWDIO; требуемый программатору VTref — отдельно подтверждённая3.3V точка |
| Команды, status, ROS / Python test | USB-UART с логическими уровнями 3.3 V | USART1: PA9 TX, PA10 RX, GND |

ST-LINK по SWD не заменяет пользовательский UART. Виртуальный COM у некоторых моделей ST-LINK можно использовать только при наличии соответствующей физической проводки; сам USB-кабель этого не создаёт. Разъёмы RS485 приводов/USART3/USART6 и host UART — разные цепи.

## 1. Снять энергию исполнительных механизмов

Отключите силовое питание колёс, насосов, клапанов, DC, stepper и сервоприводов по схеме робота. Электроника контроллера может питаться отдельно от подтверждённого источника. USB/SWD/UART способны частично подпитать плату через сигналы; не рассчитывайте, что одного выключателя достаточно, если другие источники не проверены.

Проверьте маркировку MCU и питание. Цель — STM32F407VG, Flash1MiB. Не подключайте 5 V к MCU/SWD/USART пинам. Не предполагайте, что clone ST-LINK умеет правильно питать всю плату. На оригинальном ST-LINK VTref/T_VCC — **вход измерения напряжения target**, а не разрешение подавать питание с этого контакта. Владелец подтверждает схему питания и общую землю до соединения сигналов.

По предоставленной владельцем [карте разъёмов](images/stm32-board-connectors.jpg) SWD находится над микроконтроллером и имеет подписи GND/NRST/SWCLK/SWDIO. USART1 расположен вверху и подписан GND/RX/TX. Числовые номера и вид со стороны пайки не заданы: используйте именно подписи на соответствующей стороне платы, не номера похожего clone-разъёма. На показанном SWD нет отдельного VTref; точку3.3V нужно подтвердить отдельно, +5V для этого не подходит.

## 2. Подключить SWD

Соединение по названиям сигналов:

| Сигнал программатора | На стороне STM32F407 |
|---|---|
| GND | Контакт GND разъёма SWD |
| VTref / T_VCC input | Подтверждённая опорная линия target около 3.3 V |
| SWDIO | Контакт SWDIO разъёма SWD, PA13 |
| SWCLK | Контакт SWCLK разъёма SWD, PA14 |
| NRST | Контакт NRST разъёма SWD |

Подключение NRST и режим соединения выбираются по документации конкретного ST-LINK и платы. Не соединяйте контакты только по одинаковым номерам: STDC14, ARM20, SWIM и clone headers имеют разный порядок. SWO для данной процедуры не требуется. Провода должны соответствовать известной схеме, а не вымышленному «пину 1» основной платы.

Официальные источники: [ST-LINK V3SET manual — T_VCC/SWD/NRST](https://www.st.com/resource/en/user_manual/dm00526767-stlinkv3set-debuggerprogrammer-for-stm8-and-stm32-stmicroelectronics.pdf), [STM32F405/407 datasheet](https://www.st.com/resource/en/datasheet/stm32f405rg.pdf), [официальная pin data STM32F407V(E-G)Tx](https://github.com/STMicroelectronics/STM32_open_pin_data/blob/master/mcu/STM32F407V%28E-G%29Tx.xml). Названия MCU пинов не являются схемой разъёма конкретного робота.

## 3. Подготовить инструменты и новый образ

Установите STM32CubeProgrammer с [официальной страницы ST](https://www.st.com/en/development-tools/stm32cubeprog.html). Native firmware build требует Python3, CMake/Ninja и Arm GNU, см. [INSTALL.md](INSTALL.md). Keil не нужен.

Выполненные итоговые сборки использовали безопасный default uncommissioned profile. Для собственного reviewed deployment владелец вручную выполняет новый configure/build; чужой manifest или образ нельзя объявить настроенным изменением флага. Для явного выбора CLI, если установлено несколько комплектов:

```sh
export STM32_PROGRAMMER_CLI='/absolute/path/to/STM32_Programmer_CLI'
```

В новом build-каталоге должны находиться согласованные `eurobot_next.bin` и `eurobot_next.manifest.json`, а также ELF/HEX/MAP для анализа. Manifest содержит image SHA256, размер, MCU/base, source fingerprint и hash выбранного deployment. Исходники/profile нельзя менять между проверкой и записью. Отсутствующий или устаревший fingerprint — причина **собрать заново**, не дописать hash вручную.

Только локальная проверка, без обращения к программатору:

```sh
tools/verify.sh --image build/stm32-debug/firmware/eurobot_next.bin
```

Исторический или несогласованный образ должен получить отказ свежести; текущие образы проверенного среза прошли offline verify. Успешная локальная проверка ещё не подтверждает наличие ST-LINK, читаемость Flash или работу платы.

## 4. Явно разрешённая запись

Закройте CubeIDE/debugger и другие программаторы. Владелец должен знать, что application начинается по 0x08000000 и custom bootloader не занимает эту область. Если это неизвестно, не ставьте подтверждающий флаг ради обхода отказа: такая схема загрузки требует отдельного анализа.

Только после проверки питания, проводки, нового образа и загрузочной схемы:

```sh
tools/flash.sh \
  --image build/stm32-debug/firmware/eurobot_next.bin \
  --allow-flash --confirm-no-custom-bootloader \
  --stlink-sn ACTUAL_STLINK_SERIAL
```

`ACTUAL_STLINK_SERIAL` заменяется реальным серийным номером выбранного ST-LINK. Его можно посмотреть в CubeProgrammer или командой только перечисления программаторов (без подключения к target):

```sh
"$STM32_PROGRAMMER_CLI" -l st-link-only
```

Переменная должна содержать реальный путь к установленному CLI. При единственном ST-LINK параметр `--stlink-sn` можно вообще опустить. Скрипт умеет выбрать единственный probe; при нескольких явный serial обязателен. Это номер программатора, не `/dev/cu.*`. Для CLI по другому пути можно передать `--programmer '/actual/path/STM32_Programmer_CLI'`.

Последовательность скрипта:

1. Локально проверяет образ, manifest, vectors и соответствие исходникам до любого programmer call.
2. Выбирает один ST-LINK; проверяет device ID семейства 0x413 и Flash size register. По family ID нельзя отличить все варианты MCU — маркировка платы проверяется отдельно.
3. Читает **всю внутреннюю Flash** в `backups/flash-…bin` и JSON с SHA256. Неполный/недоступный backup запрещает запись.
4. Записывает только проверенный BIN по 0x08000000, выполняет verify и halt.
5. Независимо читает записанную область и сравнивает все байты/SHA256. Нет автоматического повтора при неопределённом результате.

Нормальная запись может стирать затрагиваемые Flash sectors. Поэтому полный backup нужен даже при записи небольшого BIN. Скрипт не выполняет full erase, read-unprotect, изменения option bytes/RDP/OTP или automatic start/reset. Не обходите защиту памяти: снятие RDP может уничтожить прежнюю прошивку. Доступность чтения заранее не гарантируется.

Backup содержит только внутреннюю Flash; option bytes, внешняя память, RAM и состояние механики не входят. Сохраните копию отдельно. Это не проверенная процедура полного восстановления робота и не материал для публичного Git.

## 5. Отдельное чтение для проверки

Если владелец хочет повторно сравнить Flash с новым образом, это уже hardware access:

```sh
tools/verify.sh \
  --image build/stm32-debug/firmware/eurobot_next.bin \
  --allow-connect --stlink-sn ACTUAL_STLINK_SERIAL
```

Команда разрешает SWD и readback, но не запись. Без `--allow-connect` выполняется только локальная проверка. `verify` не принимает `--allow-flash`.

## 6. Самостоятельно запустить записанную программу

Успешная запись заканчивается `halt`: процессор может оставаться остановленным, поэтому UART ещё не обязан отвечать. Силовое питание механизмов оставьте отключённым. Закройте сеанс программатора/debugger, выключите питание логики и отсоедините SWD при снятом питании. Затем включите только питание логики заново. Это ручной запуск; скрипт его не выполняет.

Для standalone приложения штатная загрузка STM32F407 должна идти из Flash (`BOOT0=0`). Положение перемычки/кнопки BOOT0 определяйте по документации именно этой платы; её расположение неизвестно. Не меняйте option bytes. Если на плате предусмотрена документированная кнопка RESET/NRST, её использование возможно по инструкции платы; снятие и повторное включение питания логики устраняет сохранённое состояние debug halt.

Если после этого нет UART-ответа, сначала проверьте питание, загрузочный режим и TX/RX. Не подавайте питание приводов ради проверки связи.

## 7. Подключить UART для проверки с Mac

После самостоятельной записи и принятой владельцем процедуры запуска контроллера подготовьте отдельный USB-UART3.3 V. Силовое питание механизмов пока остаётся отключённым.

| STM32 USART1 | USB-UART |
|---|---|
| PA9 TX | RX |
| PA10 RX | TX |
| GND | GND |

Не используйте RS232/5V TTL. Питание адаптера не подключается к плате без подтверждённой схемы. Настройки новой прошивки —115200,8N1. Legacy921600 не используется. Найдите реальное имя `/dev/cu.*`, закройте serial monitor/ROS bridge и выполните только чтение:

```sh
python3 tools/board_test.py --port /dev/cu.usbserial-YOUR_ADAPTER
```

Дальнейшие шаги, параметры и пример явно разрешённого упражнения: [MACOS_BOARD_TEST.md](MACOS_BOARD_TEST.md). Default client только status+sensors, без claim/arm/движения. Проверка механизмов требует отдельного подготовленного стенда и известного профиля; ID254, допустимые токи и реальные пределы не исправляются догадкой. Для новой разводки8+8 все routes уже заданы в examples/board_8_pumps.hpp; сверить исполнение по BOARD_WIRING.

## При ошибке

Не повторяйте запись автоматически, не меняйте manifest/base для обхода проверки и не снимайте RDP. Оставьте силовое питание отключённым, сохраните текст ошибки и backup. Отказ из-за старых исходников решается новой сборкой; неверный device ID/Flash size — проверкой платы; ошибка SWD/backup — проверкой питания, проводки, владельца probe и защиты без разрушительных действий.

Сам факт успешной записи/readback не подтверждает boot, RTOS deadlines, механический ход или аварийный останов. Эти результаты фиксируются отдельно в [TESTING.md](TESTING.md).

## Дополнительный UART5 и сервисные проверки

Опциональный UART5: PC12TX→RX USB-UART, PD2RX←TX USB-UART, общая GND, уровни3.3V,115200/8N1. Включается только через `debug_uart_enabled` после проверки разводки. На карте UART5 подписан GND/RX/TX/+5V; подключать по подписям, +5V к USB-UART не соединять без схемы питания. USART1 и UART5 обслуживают один Controller: старый владелец/sequence/lease не обходятся вторым кабелем.

После чтения status можно прочитать `--maintenance board_info`, `diagnostic_text`, `application_state` и encoder ticks/path, если hardware profile разрешает соответствующее чтение. Подробности [MAINTENANCE.md](MAINTENANCE.md). Software BOARD_RESET сначала делает stop, передаёт ACK до UART TC и только затем reset; в этом случае клиент не посылает запросы вслед уходящей сессии. Это команда текущего firmware после загрузки, не способ прошить плату.
