# Насосы и клапаны

PumpBank рассчитан на 1–32 независимо управляемых насоса и соответствующие клапаны. Host тесты покрывают 8,16 и 32 канала. Доступное количество физически подключённых насосов задаётся отдельно: в 2026 подтверждены только 4 — силовые выходы 1/3/5/7 внешнего 24-битного регистра. Клапаны —2/4/6/8. Два legacy gripper используют одни и те же выходы, поэтому не дают 8 независимых насосов. Полная карта — PINOUT.md.

## Команда маски

Для каждого набора есть `select` и `values`: `new = (old & ~select) | values`. Биты values вне select запрещены; биты за пределами конфигурации запрещены. Насосы и клапаны проверяются вместе до единственной output transaction. Изменение не включает остальные насосы на промежуточное время.

Для восьми логических каналов:

| Требование | pumps_select | pumps_values |
|---|---:|---:|
| Включить насос 0 |0x01|0x01|
| Выключить насос 0 |0x01|0x00|
| Включить группу 0/2/7 |0x85|0x85|
| Одновременно выключить 0/1 и включить 2/3 |0x0F|0x0C|
| Выключить все 8 |0xFF|0x00|

Это примеры кодирования для подтверждённой восьмиканальной конфигурации; они не разрешают подачу питания на непроверенные нагрузки. Логический номер 0 соответствует первому каналу; номер силового разъёма и номер бита регистра могут отличаться.

Программный вызов после explicit arming проходит `Controller::pumps(owner, sequence, select, values, valve_select, valve_values, now)`. ROS2 service `set_outputs` имеет те же четыре маски и возвращает accepted/error_code/message. См. ROS2_INTERFACES.md. Напрямую вызывать PumpBank из второй задачи или отдельной debug-команды нельзя.

## Привязка к плате

Deployment::output_word / board::shift_write переводит логические каналы в фактические биты и сохраняет четыре NRST бита шаговых драйверов; неназначенные силовые выходы формируются выключенными. SPI1 передаёт байты младший/средний/старший, STCP защёлкивает новое состояние после полного завершения передачи. Транзакция должна владеть всей SPI1, поскольку L6474 использует ту же шину с другими chip-select и скоростью.

Насосы 5–8 должны получить уникальные подтверждённые силовые выходы. Один только свободный номер GPIO или существование 20 силовых выходов не доказывает запас тока и пригодность канала. Для 16 насосов с 16 клапанами потребуется 32 силовых канала, тогда как на плате подтверждено 20 плюс 4 занятых reset bits в регистре; нужен дополнительный output backend/оборудование. Масочный 32-битный API уже допускает масштабирование; физическое расширение не эмулируется фиктивными GPIO.

## Параметры и ограничения

`channels` — число логических каналов 1…32. `max_active` — предел одновременно включённых насосов; проверяется для всего нового состояния, включая незатронутые каналы. Он не вычисляет ток и не является подтверждённой мощностью блока питания. `command_timeout_ms` ограничивает время без свежей output-команды; default250 мс в переносимом ядре. `max_on_ms`, если ненулевой, ограничивает непрерывное ON каждого насоса, даже если команды ON повторяются. Конкретные значения требуют требований вакуумной системы и питания.

Тайм-аут выключает насосы и клапаны в программный ноль и снимает arming через Controller. Heartbeat не продлевает срок output-команды. Программный ноль клапанов должен быть подтверждён как допустимый в пневмосхеме; normally-open/normally-closed и active-low подключения неизвестны. До подтверждения силовой части нельзя считать безопасным автоматическое размыкание вакуума или удержание груза.

## Диагностика и ошибки

| Поле | Что означает |
|---|---|
| requested | Последняя допустимая заявка |
| commanded | Последняя передача, принятая драйвером |
| commanded_known | Биты с известным результатом передачи; при сбое обнуляются |
| measured_on | Реальные значения датчиков, если предоставлены |
| measured_known | Каналы с достоверной обратной связью; без датчиков 0 |
| fault | invalid_config/argument, not_armed, timeout, output_failure и другие ошибки |

Отказ передачи переводит результат в неизвестный, вызывает попытку безопасного отключения и требует нового arming. Даже если повторный OFF не прошёл, ошибка остаётся видимой; ПО не объявляет насос выключенным физически. Ни ACK, ни software shadow не измеряют давление, ток или состояние клапана. Устаревшие измерения должен инвалидировать их производитель.

## Проверки

В `tests/core_tests.cpp` проверяются независимые каналы, group masks, одна output-запись на команду, запрещённые биты, max_active, timeout, непрерывный ON, переполнение миллисекунд, output failure и requested/commanded/measured semantics. Полный путь через Dispatcher проверяет owner/sequence/arming/CRC. Драйверные проверки должны подтверждать точный порядок SPI байтов, сохранение reserved bits и отсутствие лишнего all-on latch.

Аппаратно после отдельного разрешения: проверить схемой нагрузки и current limit, на отключённом питании нагрузок записать 0→маска→0 и наблюдать STCP/SPI; затем с ограничением тока проверить один насос/клапан, пары, максимальную разрешённую группу, потерю high-level и отказ SPI. Измерить ток пуска, частоту переключения и задержку OFF. Отдельно испытать hardware emergency isolation и перезапуск MCU с питанием исполнительных механизмов. Все аппаратные результаты пока открыты.

Полная целевая сборка этого backend выполнена в debug/release и экспериментальном C++26, ; профильные проверки входят в общий CTest. Число физических независимых насосов по исходной проводке по-прежнему 4; host-проверка маски 8/16/32 не заменяет расширение силовой части.

## Обновление новой редакции: отдельные deadlines каналов

Command timeout учитывается для каждого выбранного pump/valve отдельно. Refresh каналаB не удерживает каналA. Принятый и авторизованный finite job продлевает только ресурсы, перечисленные во всём его плане, в том числе уже активные удержания до фазыOFF; выключенный ресурс от этого не включается. Посторонние каналы не продлеваются. После завершения job действует обычный250ms timeout без автоматического удержания. Max-on остаётся отдельным пределом и не снимается refresh. Поведение проверяется текущим core/runtime suite; результаты свежего прогона приведены в VALIDATION_REPORT.
