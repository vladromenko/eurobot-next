# План аппаратной проверки: общий DIAGNOSTIC_PROFILE, затем один механизм

Эта инструкция относится к существующему EUROBOT_NEXT и той же синей STM32F407-плате. Год установленной старой прошивки не определяет фактические ID, комплект механизмов или соответствие жгута исходникам2025/2026. В этой работе физическую плату не прошивают и опасные команды не выполняют. Установку выполняет владелец отдельно по [WHAT_I_NEED_TO_DO.md](../WHAT_I_NEED_TO_DO.md).

Программная поддержка устройств, source-кандидаты2025/2026, фактическая проводка и будущая разводка8 насосов — разные вещи. Первым устанавливается общий **DIAGNOSTIC_PROFILE в DIAGNOSTIC_MODE** (`stm32-diagnostic`/диагностический Debug), выбранный главным документом комплекта. Не использовать старый установщик рабочего профиля2026 или произвольный BIN из build-каталогов как первый образ.

## Что разрешено на каждом этапе

| Этап | Что проверять | Что не выполнять |
|---|---|---|
| До установки NEXT, произвольная прежняя прошивка | маркировки, обесточенная проводка, backup/идентификация по отдельной инструкции | не посылать ей команды NEXT; несовпадение протокола не лечится подбором управляющих пакетов |
| Первый NEXT, DIAGNOSTIC_MODE | status, deployment_info, board_info, GPIO; отдельные безопасные read-only device queries после проверки интерфейса | arm, torque enable, PWM, шаги, выходы насосов/клапанов, изменяющие maintenance и Gripper jobs заблокированы |
| Подтверждённый OPERATIONAL_MODE | один разрешённый механизм, минимальное согласованное воздействие | неизвестные маршруты/ID/пределы, автоматические сценарии и одновременное включение всей механики |
| После индивидуальной приёмки | проверенный сценарий, затем совместные ресурсы и ROS motion | принимать ACK/settled за измеренный захват, давление или доказанное снятие энергии |

Переход в OPERATIONAL_MODE — явное изменение и новая сборка проверенного профиля с разрешёнными устройствами, commissioned/valid, затем самостоятельная установка и **новый явный arm**. Это не ROS-параметр, не команда обхода режима и не снятие safety-проверок. Для каждого воздействия сначала подтвердить профиль в работающей плате, а не только имя скачанного BIN. `valid=true` проверяет согласованность программной конфигурации, не физическую проводку.

## Общая подготовка и протокол остановки

1. Отключить энергию исполнительной части. Подтвердить питание логики и общую землю по [BOARD_WIRING.md](BOARD_WIRING.md); не угадывать, что +12V достаточно для логики. Не использовать питание USB-UART/ST-LINK как неизвестный источник питания всей платы. Не менять силовые соединения под напряжением.
2. Шасси закрепить с поднятыми колёсами; лифт и груз поддержать независимо от torque/тока шаговика. Очистить весь предполагаемый ход механизма, обеспечить наблюдение и доступный независимый разрыв силового питания. Первые испытания без полезного груза.
3. Для подключения UART использовать USART1: TX платы→RX адаптера, RX платы←TX адаптера, общая GND; уровни3.3V. Физические контакты определять по карте и подписям, не по придуманной нумерации. SWD — отдельный интерфейс.
4. Один владелец последовательного порта: закрыть ROS bridge/старую панель/serial monitor перед Mac-клиентом. Не пытаться отобрать порт или lease. После Mac-теста клиент должен завершиться и закрыть порт, прежде чем запускается ROS.
5. В физическом нештатном движении первым действием снять энергию аппаратным stop. Не ждать ответа UART. В управляемом упражнении `Ctrl-C` инициирует конечный cleanup: ESTOP/release. Ошибка cleanup означает **остановка не подтверждена**, а не разрешение повторить команду. ESTOP после упражнения намеренно остаётся защёлкнутым; следующий тест требует нового явного arm.
6. `board_test.py --exercise ... --allow-motion` и `actuator_test.py --allow-motion` сами создают новую ограниченную сессию, подтверждают arm и в конце останавливают/освобождают её. Они не переподключаются и не повторяют потерянную команду. Повтор позиции/DC — только заранее разрешённое поддержание новой свежей командой; шаги и home отправляются один раз. ACK означает приём команды, не измеренное достижение цели.

**Все блоки ниже — инструкция для владельца, а не журнал выполненного HIL.** Записывать PASS только по реальному наблюдению и измерению. Положение руки/предмета/давление не выводится из software ACK.

## Первый сеанс Mac: только чтение

Только после самостоятельной установки выбранного диагностического NEXT. В Terminal:

```sh
cd /Users/vladromenko/Desktop/Eurobot/EUROBOT_NEXT
mkdir -p artifacts/hardware-acceptance
ls /dev/cu.*
```

По списку выбрать свой USB-UART. Затем вручную присвоить `PORT` фактический путь; строка с REPLACE является примером, её нельзя считать найденным устройством:

```sh
PORT='/dev/cu.usbserial-REPLACE_WITH_ACTUAL_ADAPTER'
set -o pipefail
python3 tools/board_test.py --port "$PORT" --maintenance deployment_info \
  | tee artifacts/hardware-acceptance/01-deployment.jsonl
python3 tools/board_test.py --port "$PORT" --maintenance board_info \
  | tee artifacts/hardware-acceptance/02-board.jsonl
python3 tools/board_test.py --port "$PORT" --maintenance diagnostic_text \
  | tee artifacts/hardware-acceptance/03-diagnostics.jsonl
python3 tools/board_test.py --port "$PORT" --maintenance gpio \
  | tee artifacts/hardware-acceptance/04-inputs.jsonl
```

Каждый запуск сначала читает status/sensors и не захватывает сессию. Для общего диагностического образа ожидается `mode=diagnostic`, `profile=CUSTOM`, `armed=false`, исходно отсутствие чужой lease/owner; неизвестные/отключённые измерения остаются unknown/null. `commissioned=false` и `valid=false` для не допущенной к движению кандидатной конфигурации не являются поводом включить её силовую часть. `deployment_info` — read-only op37: body schema1, mode0diagnostic/1operational, profile0CUSTOM/1ROBOT_2025_HARDWARE_PROFILE/2ROBOT_2026_SOURCE_PROFILE, commissioned, valid, channels, max_active. Сверить значения с manifest/главным документом текущей сборки.

Если ответ вообще отсутствует или возвращается неправильная длина/CRC — остановиться по [FIRST_RUN_TROUBLESHOOTING.md](FIRST_RUN_TROUBLESHOOTING.md). Старая2025 не обязана отвечать протоколом NEXT. Не повышать timeout до бесконечности и не включать legacy-команды «для проверки».

Ниже read-only опрос внешнего устройства разрешён только после идентификации его интерфейса и проверки, что его безопасное питание не включает движение. Не опрашивать весь ID-диапазон автоматически. Отсутствие ответа обесточенного устройства ожидаемо; не записывать это как повреждение драйвера.

## Перед каждым испытанием движения

Провести повторный `deployment_info`. Для операционных блоков нужны `mode=operational`, `commissioned=true`, `valid=true`, согласованный профиль именно существующего жгута, известные допустимые ток/напряжение/ход/скорость и проверенная остановка. В DIAGNOSTIC_MODE все эти блоки **BLOCKED**.

В примерах `${NAME:?описание}` намеренно не имеет значения по умолчанию: shell откажет в запуске, пока оператор явно не задаст проверенное значение. Это шаблоны параметров, **не безопасные заводские настройки**. Имя переменной не заполняется по фото автоматически. Не заменять неизвестные limits произвольными числами, полным ходом0..255mm или source-настройкой калибровки400000TPM.

## 1. Шасси целиком

- **Подключить/отключить:** после read-only этапа оставить необходимые контроллеры колёс/энкодеры; остальные механизмы отключены по энергии. Поднять все колёса и закрепить базу. Не начинать с движения по столу/полу.
- **До движения:** получить `wheel_ticks`, `wheel_path`, проверить `known_mask` всех нужных колёс, IDs и порядок колёс по профилю. Нулевой known-mask — запрет перехода к движению, а не исправный ноль.
- **Минимальное воздействие, только OPERATIONAL_MODE:** сначала отдельно принять каждое колесо в процедуре2; затем один короткий `timed_move`, одна ось, согласованная малая скорость/длительность:

  ```sh
  python3 tools/board_test.py --port "$PORT" --exercise gripper --allow-motion \
    --gripper "${TEST_GRIPPER_NUMBER:?Проверенный маршрут1или2}" \
    --operation timed_move --mask "${TEST_BASE_AXIS:?0X_1Y_2yaw}" \
    --value "${TEST_BASE_VELOCITY:?Согласованная_m_s_либо_rad_s}" \
    --argument "${TEST_BASE_DURATION_MS:?Согласованное_время_ms}" \
    --job-timeout-ms "${TEST_JOB_TIMEOUT_MS:?Проверенный_конечный_срок100_60000}"
  ```

- **Ожидается:** вращение соответствует выбранной системе координат и профилю; неподвижные оси не превращаются в дрейф; все колёса прекращают получать тягу после конца. Source-геометрия не доказывает направление физических проводов.
- **Остановка/сбой:** Ctrl-C запускает cancel/ESTOP/release; любое нежелательное движение — аппаратный stop. Не исправлять знак общей скорости, пока не проверены порядок, знак каждого мотора и энкодера. Не повторять потерянный job.
- **Сохранить:** видео всех колёс, выбранные параметры/ось, known-mask, начальные/конечные ticks, job/stop errors, фактическое время остановки и hash/profile образа. Проверка движения на полу — отдельный допуск после этого стенда.

## 2. Каждый колёсный двигатель отдельно

- **Подключить/отключить:** колёса подняты, механика закреплена. Контроллеры, которые нужны протоколу/feedback шасси, могут оставаться на подтверждённом логическом питании; ненужная механическая нагрузка отсутствует. Не считать DC/PWM индексом адрес Maxon.
- **Только чтение:** для каждого `WHEEL_INDEX=0,1,2` выполнить отдельно:

  ```sh
  python3 tools/board_test.py --port "$PORT" --maintenance device_ping \
    --channel 0 --arg "${WHEEL_INDEX:?Проверенный_индекс0_2}"
  python3 tools/board_test.py --port "$PORT" --maintenance motor_range \
    --channel "${WHEEL_INDEX:?Проверенный_индекс0_2}"
  ```

  Ping подтверждает ответ адреса из текущего профиля, а не его физическое имя или безопасную скорость. Исторические2025/2026 IDs не подменяют проверку жгута.
- **Минимальное воздействие:** существующая команда `wheel_calibration` двигает только выбранное колесо, но использует **параметры из скомпилированного** `grippers[...].drive_reference`: `wheel_tpm`, `wheel_goal_ticks`, `wheel_stop_margin`. До испытания создать reviewed тестовый профиль с измеренно допустимой малой скоростью и малым ходом; проверить эти значения в исходнике выбранного профиля и manifest. **Стандартные400000TPM/28×4096ticks нельзя использовать как первую малую проверку.** Если малые параметры ещё не утверждены — тест движения BLOCKED.

  ```sh
  python3 tools/board_test.py --port "$PORT" --exercise gripper --allow-motion \
    --gripper "${TEST_GRIPPER_NUMBER:?Проверенный_маршрут}" \
    --operation wheel_calibration --mask "${WHEEL_INDEX:?Индекс0_2}" \
    --job-timeout-ms "${TEST_JOB_TIMEOUT_MS:?Конечный_срок_тестового_профиля}"
  ```

- **Ожидается:** работает ровно выбранное колесо, правильный знак ticks, наблюдаемый небольшой ход; другие команды колёс нулевые. Успех не измеряет PID-качество внешнего Maxon-контроллера.
- **Остановка/сбой:** общий stop немедленно при другом колесе/направлении. Не применять `motor_id`, `motor_range` mutation или перекоммутацию под питанием, чтобы скрыть ошибку адресации.
- **Сохранить:** отдельная строка приёмки для каждого индекса, фото физического колеса и контроллера/ID, raw range, команда, ticks до/после, видео и время stop. Для дополнительного DC-мотора отдельного H-bridge использовать `actuator_test.py --kind dc_duty`, только с проверенными ID/знаком/duty/окном, по правилам раздела4 для примитивного клиента.

## 3. Энкодеры

- **Подключить/отключить:** силовой привод запрещён, но контроллер и энкодер имеют подтверждённое питание, допускающее чтение. Не вращать механизм вручную, если редуктор/нагрузка этого не допускают; не полагаться на отключённый torque как на удержание груза.
- **Минимальная проверка:** снимок до/после одного помеченного малого ручного поворота, если такой поворот разрешён конструкцией. Иначе использовать уже разрешённую малую проверку выбранного колеса из2.

  ```sh
  python3 tools/board_test.py --port "$PORT" --maintenance wheel_ticks
  python3 tools/board_test.py --port "$PORT" --maintenance wheel_path
  ```

- **Ожидается:** known-mask выставлен только для реальных ответов; меняется соответствующий счётчик, знак обратного поворота противоположен, масштаб согласуется с реальным encoder/редуктором. `path` — расчёт по калибровке, не независимая линейка. Переполнение int32 учитывать как модульное изменение, не скачок физического пути.
- **Остановка/сбой:** прекратить вращение; не сбрасывать счётчики, чтобы стереть ошибку. `reset_wheel_ticks` и `set_pose` — изменения, не часть первого read-only этапа. При неустойчивых данных проверить питание/кабель/землю/порядок/кодирование до изменения коэффициентов.
- **Сохранить:** два raw снимка, известность, физический угол/число оборотов и метод измерения, знак, какая ось двигалась, обороты моторного/выходного вала и применённый gear ratio.

## 4. Dynamixel AX/MX

- **Подключить/отключить:** один идентифицированный привод на подтверждённом USART3/DIO адаптере с верными уровнями/DE/питанием; прочие механизмы обесточены либо механически освобождены. Маркировка реального AX/MX важнее имени старого файла. Не использовать254/255, не менять ID широковещательно.
- **Только чтение:** задать `SERVO_ID` по уже идентифицированному устройству, а не по всем свободным адресам:

  ```sh
  python3 tools/board_test.py --port "$PORT" --maintenance servo_probe \
    --channel "${SERVO_ID:?Подтверждённый_индивидуальный_ID1_253}"
  python3 tools/board_test.py --port "$PORT" --maintenance servo_feedback \
    --channel "${SERVO_ID:?Подтверждённый_ID}"
  ```

  Сохранить model_number, firmware, actual_id, raw CW/CCW limits, present_position, torque и return level. Raw limits/позиция модель-зависимы; не применять автоматически300°/1023 к неизвестной модели. ID2026 primary112 и cursor98 не являются утверждением о нынешнем неизвестном жгуте.
- **Минимальное воздействие:** только проверенный абсолютный target возле измеренного текущего положения, без пересечения упора. `actuator_test` явно включает torque **этого** AX/MX; значения для этих двух kinds в **радианах**, не градусах. Выбрать `TEST_ACTUATOR_KIND=ax_position` или `mx_position` по модели:

  ```sh
  python3 tools/actuator_test.py --port "$PORT" --allow-motion \
    --kind "${TEST_ACTUATOR_KIND:?ax_position_или_mx_position_по_модели}" \
    --id "${SERVO_ID:?Подтверждённый_ID}" --value "${TEST_TARGET_RAD:?Проверенная_абсолютная_цель_rad}" \
    --duration-ms "${TEST_ENERGIZATION_MS:?Разрешённое_окно1_10000ms}"
  ```

- **Ожидается:** только выбранный привод выполняет малое правильное перемещение, обратная связь согласуется с измерением. Helper удерживает свежую позиционную команду только в заданном окне; это не самостоятельная проверка достижения цели.
- **Остановка/сбой:** после окна ESTOP/release снимает разрешение; torque removal может освободить механизм, поэтому его заранее поддерживают. Не делать ID assignment/torque-limit EEPROM mutation для лечения отсутствующего ACK. Потеря ACK — неизвестный исход, не повтор команды.
- **Сохранить:** фото модели/ID, probe/feedback, target с единицами, фактический угол/направление, видео, ток/нагрев при доступном подтверждённом измерителе, cleanup errors.

## 5. PWM/PCA-сервоприводы

- **Подключить/отключить:** один выбранный RC servo/PCA канал; реальная питающая шина, pulse min/max/range, частота и начальное положение подтверждены. Рычаг снять или освободить до первого импульса по возможности конструкции. +6V/+5V на карте не задают номинал конкретного servo.
- **Диагностика:** `pwm_info --channel0` и затем1 показывают timer frequency/ARR для двух групп STM32; не доказывают физический PWM, присутствие PCA или угол вала. В DIAGNOSTIC_MODE импульсы движения не включать. Read-only аппаратного feedback PCA-угла в этой системе нет.

  ```sh
  python3 tools/board_test.py --port "$PORT" --maintenance pwm_info \
    --channel "${PWM_GROUP:?Проверенная_группа0_1}"
  ```

- **Минимальное воздействие:** после OPERATIONAL-допуска один известный target в градусах; `pwm_servo` ID0..7 соответствует логическим PWM1..8, `pca_servo` ID0..15 — реальному нулевому номеру канала PCA. Не путать с Power Output.

  ```sh
  python3 tools/actuator_test.py --port "$PORT" --allow-motion \
    --kind "${TEST_PWM_KIND:?pwm_servo_или_pca_servo}" \
    --id "${TEST_PWM_CHANNEL:?Проверенный_логический_канал}" \
    --value "${TEST_TARGET_DEG:?Проверенный_абсолютный_угол_градусы}" \
    --duration-ms "${TEST_ENERGIZATION_MS:?Разрешённое_окно_ms}"
  ```

- **Ожидается:** сигнал только на выбранном канале; период/длительность сначала проверить осциллографом при отключённом servo, если есть доступ к измерению, затем малое движение. Время выдержки/ACK не являются measured angle.
- **Остановка/сбой:** ESTOP прекращает управление согласно backend; аппаратно снять питание при неверном канале/рывке. Не подавать ALL_PULSE на16каналов и не менять общий timer/PCA frequency, пока другие подключённые нагрузки не отключены и влияние не рассмотрено.
- **Сохранить:** channel→connector, модель, напряжение, частота/осциллограмма, pulse limits из профиля, заданный/измеренный угол, cleanup.

## 6. Шаговые двигатели и концевики

- **Подключить/отключить:** один проверенный Stepper Output, пары обмоток/ток/режим шага/полярности/направление подтверждены, вал без опасной нагрузки. Не отсоединять обмотки при питании драйвера.
- **Только чтение:** GPIO до/во время ручного срабатывания **проверенного** концевика; одновременно проверить filtered `application_state`. Не коротить случайный разъём. Для выбранного драйвера отдельно:

  ```sh
  python3 tools/board_test.py --port "$PORT" --maintenance gpio
  python3 tools/board_test.py --port "$PORT" --maintenance application_state
  python3 tools/board_test.py --port "$PORT" --maintenance stepper_parameter \
    --channel "${STEPPER_INDEX:?Логический_канал0_3}" --arg 0
  ```

  Raw L6474 status — состояние драйвера, не датчик абсолютной позиции и не доказательство software reference. Сохранить fault bits; не выполнять hard reset/GET_STATUS лишь для скрытия причины.
- **Минимальный home:** разрешён только с mapped реальным home input и проверенным направлением/расстоянием, по согласованной малой скорости:

  ```sh
  python3 tools/actuator_test.py --port "$PORT" --allow-motion \
    --kind stepper_home --id "${STEPPER_INDEX:?Проверенный_индекс}" \
    --value "${HOME_DIRECTION:?Проверенное0назад_или1вперёд}" \
    --rate "${HOME_RATE_STEPS_S:?Подтверждённая_скорость_целые_шаги_с}" \
    --duration-ms "${TEST_ENERGIZATION_MS:?Окно_в_пределах_разрешённого_поиска}"
  ```

- **Ожидается:** ход к правильному концевику и прекращение шагов при срабатывании/сроке. Клиент посылает home один раз, затем только heartbeat; его exit0 подтверждает приём/cleanup, **не завершённый home**. Поиск без концевика запрещён.
- **Reference после stop:** ESTOP/release в конце отдельного helper-теста намеренно инвалидирует reference. Нельзя выполнить home в одном процессе, а затем считать следующий процесс relative/lift уже откалиброванным. Относительное движение требует verified home и движения **в одной непрерывной owned armed сессии** с подтверждённым reference; пока такой путь не принят, тест relative — BLOCKED. Не обнулять программно позицию вместо концевика.
- **Остановка/сбой:** ручной stop при движении от концевика/упоре/пропуске шагов. Зафиксировать сырые GPIO, status, ток, направление; проверить карту и полярность, не удлинять поиск без проверки механического хода.
- **Сохранить:** фото обмоток/разъёма, driver/current/step-mode, home input electrical+filtered states, скорость, пройденное расстояние, время остановки, видео и факт последующего invalid reference.

## 7. Лифт

- **Подключить/отключить:** лифт без груза, независимая механическая поддержка, подтверждённые end stops, направление, ограничение хода/тока и безопасное поведение при снятии torque. Исторические25steps/mm, 1100/320mA и uint8 высота не являются измеренными пределами текущей механики.
- **До движения:** пройти процедуры3,6 и подтвердить единицы/ноль/направление/масштаб на реальном лифте. Снятие питания не должно приводить к опасному падению; иначе сначала решить удержание механически/профилем, а не отменять stop.
- **Доступная проверка сейчас:** только read-only концевик/driver status и один ограниченный home из6 с механической опорой. Прямой следующий `board_test --operation lift_height` создаёт новую сессию и не сохраняет reference завершённого home, поэтому не является рабочей последовательностью «home→lift».
- **Движение лифта пока BLOCKED:** нужен принятый same-session путь home→подтверждённый reference→малая высота, с непрерывной owned armed сессией. Нынешний job корректно требует known reference; этот документ не предлагает фиктивную задержку или повторный arm вместо него. До добавления/приёмки такого пути runnable-команды подъёма здесь намеренно нет. После его появления target задают в измеренных mm от реального нуля, а параметры/feedback фиксируют в протоколе.
- **Ожидается:** малый вертикальный ход с нужным знаком и известным reference, без удара и потери высоты после stop. `referenced_steps` означает отсчёт шагов от reference, а не независимое измерение линейкой.
- **Остановка/сбой:** аппаратно остановить при неверном направлении/скольжении; поддержка уже должна удерживать механизм. Не задавать большой ход для «поиска нуля» и не повторять timeout goal.
- **Сохранить:** мм по линейке против шагов/target, ноль/концевик/передаточное отношение, ток вверх/вниз, что происходит при stop, job phase/evidence/error/stop_error.

## 8. Отдельные механизмы захвата

- **Подключить/отключить:** только выбранный курсор/пара боковых/основной поворот/слайдер, без блока/пальцев в зоне хода; насосы и шасси по энергии выключены. Каждая ServoBinding/ID/угол уже принята индивидуально.
- **Минимальная команда:** выбрать один реально настроенный простой operation (`cursor`, `side_grips`, `rotate_main` или `slide`), одно согласованное положение. Не использовать автоматически значения/роли2026 на неизвестном жгуте:

  ```sh
  python3 tools/board_test.py --port "$PORT" --exercise gripper --allow-motion \
    --gripper "${TEST_GRIPPER_NUMBER:?Проверенная_группа1_2}" \
    --operation "${TEST_SIMPLE_GRIP_OPERATION:?Принятая_простая_операция}" \
    --value "${TEST_SIMPLE_GRIP_VALUE:?Проверенное_состояние_либо_mm}" \
    --job-timeout-ms "${TEST_JOB_TIMEOUT_MS:?Конечный_срок}"
  ```

- **Ожидается:** работает только указанная группа, не курсор вместо main/другая сторона, обратная связь соответствует target. Для связанных пар проверить оба реальных привода. Исторический broadcast254 не является физическим ID; применение2026 single112 — отдельная source-интерпретация, не предположение о нынешнем роботе.
- **Остановка/сбой:** cancel/ESTOP глобально останавливает разрешённую сессию. При чужом канале отключить энергию, исправлять binding только после сверки маркировки и жгута.
- **Сохранить:** операция/значение/единицы, ID↔механическая роль, обе стороны/два feedback, target/факт, каждый шаг/evidence, фото безопасного зазора.

## 9. Насосы по одному

- **Подключить/отключить:** один идентифицированный насос без предмета, подтверждённое номинальное питание, ключ/защита/предохранитель и допустимый ток/время. Все прочие насосы и клапаны первоначально выключены. Не перепроводить старую систему на PO1–PO16 по примеру8пар автоматически.
- **До включения:** проверить логический bit→конкретный PO и обратную полярность ключа по карте. PO — коммутируемый возврат низкой стороны, не +питания. Source четыре общие пары и будущие8пар не взаимозаменяемы.
- **Минимальное воздействие:** только один подтверждённый pump bit, маска является **логической**, не номером PO. Выбрать короткую длительность по рейтингу насоса/допуску питания:

  ```sh
  python3 tools/board_test.py --port "$PORT" --exercise output --allow-motion \
    --select "${TEST_PUMP_ONE_BIT_MASK:?Один_проверенный_логический_bit}" \
    --values "${TEST_PUMP_ONE_BIT_MASK:?Тот_же_bit}" \
    --duration-ms "${TEST_OUTPUT_DURATION_MS:?Разрешённое_окно1_5000ms}"
  ```

- **Ожидается:** включился ровно этот насос, ток/нагрев/напряжение в измеренном допустимом диапазоне; после stop он выключен. `commanded_known` — подтверждённая отправка, не датчик тока/вакуума. Без измерителя вакуума не объявлять давление measured.
- **Остановка/сбой:** аппаратный stop при чужом насосе/просадке/нагреве; проверить low-side/защиту/проводку/ток отдельно. Не повышать max_active до8, потому что восемь каналов есть в API.
- **Сохранить:** маркировка/номиналы насоса, PO и logical bit, фото подключения, стартовый/устоявшийся ток, напряжение, длительность/температура, время off и masks/known.

## 10. Клапаны по одному

- **Подключить/отключить:** один клапан с известными NO/NC/бистабильностью, напряжением/током/защитой и допустимым временем включения; давление сброшено, насосы выключены. Трубки и механика безопасны при любом положении клапана.
- **Минимальное воздействие:** один valve bit, насосные select/values не задавать:

  ```sh
  python3 tools/board_test.py --port "$PORT" --exercise output --allow-motion \
    --valve-select "${TEST_VALVE_ONE_BIT_MASK:?Один_проверенный_логический_bit}" \
    --valve-values "${TEST_VALVE_ONE_BIT_MASK:?Тот_же_bit}" \
    --duration-ms "${TEST_OUTPUT_DURATION_MS:?Разрешённое_окно1_5000ms}"
  ```

- **Ожидается:** электрически сработал только выбранный клапан и его фактическая пневматическая функция совпадает с картой. После снятия питания реальное NO/NC состояние проверено. Щелчок не доказывает герметичность/давление.
- **Остановка/сбой:** прекращение выхода не гарантирует сброс давления в любой схеме. Использовать заранее предусмотренный безопасный пневматический сброс/энергоизоляцию, затем проверить трубки и полярность. Не лечить обратный клапан перестановкой pump/valve bit вслепую.
- **Сохранить:** маркировка, NO/NC и схема трубок, PO↔bit, ток/длительность, состояние без питания/с питанием, давление при наличии датчика, masks.

## 11. Сценарии захватов

- **Подключить/отключить:** все используемые данным планом устройства уже имеют индивидуальную приёмку; остальное выключено. Реальная конфигурация платы не наследует `capture/prepare`2026 автоматически. Выбранный composite/recipe должен быть reviewed именно для жгута, с проверенными resource masks и stop.
- **Первый проход:** без предметов и без шасси, если проверенный план допускает такой отдельный этап. Нельзя просто выключить нужный плану датчик/мотор и считать timeout нормальным успехом. Если план включает motion/pumps, сначала принять их процедуры1/9/10; до этого весь такой план BLOCKED.
- **Команда:** один выбранный и согласованный recipe, без автоматического цикла повторений:

  ```sh
  python3 tools/board_test.py --port "$PORT" --exercise gripper --allow-motion \
    --gripper "${TEST_GRIPPER_NUMBER:?Проверенная_группа}" \
    --operation "${TEST_RECIPE_OPERATION:?Recipe_принятый_для_этого_профиля}" \
    --mask "${TEST_RECIPE_LOCAL_MASK:?Проверенная_local_маска0_15}" \
    --job-timeout-ms "${TEST_JOB_TIMEOUT_MS:?Конечный_срок_реального_плана}"
  ```

- **Ожидается:** шаги в утверждённом порядке, только свои ресурсы, один job ID/owner, конечная фаза/ошибки, остановка по timeout/cancel без replay. Одновременно второй job не запускается; независимые ресурсы проверять только после одиночной приёмки.
- **Доказанность:** commanded — отправка, settled — время, referenced_steps — шаги от нуля, measured — соответствующая обратная связь. Даже `physically_verified` action относится к требуемым измерениям плана, не автоматически к удержанию предмета/давлению/камере. Захват предмета проверяется отдельным наблюдением/датчиком. Camera/VLM не являются MCU-механическим capture.
- **Остановка/сбой:** cancel/ESTOP глобально останавливает разрешённые выходы; прежняя velocity не должна возобновляться. При unknown outcome не повторять job, сначала физически убедиться в остановке и снять снимки. Сохранить план, job ID, feedback каждой фазы, terminal/error/stop_error, видео синхронно с журналом, измерение удержания/давления отдельно.

## 12. ROS2: диагностика, затем управление

### Read-only соединение

Mac-клиенты должны быть закрыты. Реальный bridge запускать на поддерживаемой Ubuntu с прямым доступом к выбранному USB-UART; Docker Desktop на Mac подтверждает software build/tests, но не предоставляет автоматически Linux-контейнеру Mac `/dev/cu.*`. Не считать удачный Docker build успешным физическим UART.

На Linux, из корня той же версии проекта после сборки по [ROS2_BUILD.md](ROS2_BUILD.md):

```sh
source /opt/ros/jazzy/setup.bash
source ros2_ws/install/jazzy/setup.bash
ros2 run eurobot_hardware eurobot_bridge --ros-args -r __ns:=/eurobot \
  -p port:="${ROS_SERIAL_PORT:?Подтверждённый_Linux_путь_адаптера}" \
  -p baud:=115200 -p maintenance_enabled:=false
```

Во втором терминале с тем же ROS environment/domain:

```sh
ros2 topic echo /eurobot/state --once
ros2 topic echo /eurobot/board_inputs --once
ros2 topic echo /eurobot/diagnostics --once
ros2 service call /eurobot/maintenance eurobot_interfaces/srv/Maintenance \
  '{control_token: 0, operation: 37, channel: 0, argument: 0, secondary: 0, values: [0.0, 0.0, 0.0]}'
```

Ожидаются connected/state_valid, disarmed, diagnostic mode/profileCUSTOM; отсутствие arm и изменений выходов. Responses data op37 декодируется по указанному7B контракту; отсутствие known не превращать в нулевое измерение. Прочитать unsupported/invalid_config отдельно от transport fault. Сохранить ROS distro/domain, node/topic/service lists, state/diagnostics и firmware profile/hash. В этом этапе `arm`, SetActuator, SetOutputs и action не вызываются.

### После аппаратного допуска к OPERATIONAL_MODE

Только один publisher `/eurobot/cmd_vel` и одна текущая token-сессия. Arm через:

```sh
ros2 service call /eurobot/arm eurobot_interfaces/srv/Arm \
  '{control_token: 0, maintenance_session: false}'
```

Записать ненулевой `control_token` из принятого ответа. Его используют SetActuator/SetOutputs/Gripper этого оператора. Не брать token из старого журнала. После arm/cancel/освобождения motion reservation publisher должен выдавать **новые** `TwistStamped`: frame `base_link`, согласованные часы, source stamp строго позже границы+50ms, возраст не более200ms. Одиночный `ros2 topic pub` со статическим stamp не является потоком управления. Использовать настоящий stamped publisher из проверенного верхнего уровня; перед первым движением он ограничен принятыми в1 малыми параметрами и имеет доступный stop.

Сначала проверить `/disarm` на пустой вооружённой сессии без движения; затем отдельно один принятый малый primitive/action. Потерю потока cmd_vel, исчезновение owner/lease, UART disconnect, action cancel и publisher conflict проверять по одному, с поднятыми колёсами и записью физического времени stop. Не устраивать аварийное отключение протокола на нагруженном лифте без опоры.

Универсальная программная остановка из работающего ROS environment:

```sh
ros2 service call /eurobot/emergency_stop std_srvs/srv/Trigger '{}'
ros2 service call /eurobot/disarm std_srvs/srv/Trigger '{}'
```

Ожидается остановка выходов, disarmed и отсутствие auto-arm/replay после reconnect; новый операторский arm обязателен. Если нет подтверждения или механизм продолжает двигаться — аппаратный stop, затем журнал. Cancel, пришедший после подтверждённого COMPLETED, может вернуть SUCCEEDED; это не ложный CANCELLED и не основание повторять задачу. MCU fault может дать один final query-only snapshot после disarm: сохранить исходную job/stop error; он не возвращает actuation authority.

## Форма протокола для каждого устройства

Копировать отдельную запись, не один общий PASS на робота:

```text
Дата/оператор:
BIN SHA256 + manifest/source fingerprint:
Mode/profile/commissioned/valid:
Устройство/фото/физический разъём/ID/логический канал:
Подтверждённые питание/ток/предохранитель/механический ход:
Что было подключено и что отключено:
Команда и все числовые параметры с единицами:
Состояние/known-mask до:
Фактическое движение/ток/угол/давление + метод измерения:
Состояние/known-mask после, phase/evidence/errors:
Остановка: команда/реакция/измеренное время/падение или удержание:
Журнал/видео/фотографии:
Результат PASS / FAIL / BLOCKED; следующий разрешённый шаг:
```

Программные проверки из журнала сборки имеют статус SOFTWARE_READY. Реальная аппаратура до такой записи — HARDWARE_TEST_REQUIRED; неизвестный профиль — HARDWARE_CONFIGURATION_REQUIRED; движение в DIAGNOSTIC_MODE — BLOCKED. Эти статусы не подменяются наличием реализации драйвера в ELF.
